# 架构分析：HARNESS 指令体系深度评估

> 评估对象：`src/api/harness.ts` 指令注册表 + 配套的 `statechange.ts`（统一写接口）、`brain.ts`（中枢审查）、`steering.ts`（分级/干预/审计）、`director.ts`/`autorun.ts`（写章管线/连载）、`planner.ts`（弧边界）、`chronicler.ts`（记账）、`limiter.ts`/`titlelock.ts`（调度/锁）、`routes.ts`（路由层调用点）。
> 评估方法：纯只读代码审阅，不修改代码。所有结论附 file:line 证据。
> 关联文档：[HARNESS.md](./HARNESS.md)（指令注册表设计提案）、[ARCHITECTURE.md](./ARCHITECTURE.md)（中枢模型基线）、[DEEP-DIVE.md](./DEEP-DIVE.md)（触发点/状态闸门）。

---

## 一、总体定位

`harness.ts` 是一份"影响小说的行为"的**声明性指令注册表**（88 条），配合 `statechange.ts`、`brain.ts`、`steering.ts` 构成"中枢架构"。HARNESS.md §5 自述状态为"设计提案，分 P0–P3 落地"，当前处于 **P1–P2 之间**：登记与审计已铺开，但统一写闸门（gate）尚未接线。

HARNESS.md 头部明确："**状态：设计提案，尚未实现**。本文只整理架构、不修改代码。"——即文档先行、代码分阶段收敛。本评估即检验"声明"与"实现"的对齐度。

## 二、问题一：指令是否完备、详细、足够使用、足够明确？

### 2.1 完备性 —— 覆盖面合格，但统计与边界缺口

**优点**
- 7 大类 88 条，按 `routes.ts` 45 端点 + 内部函数动作交叉盘点，HARNESS.md §4 有覆盖矩阵与负向确认（排除纯只读函数如 `progressGuard`/`isBookComplete`）。
- 每条指令 11 字段（id/name/category/trigger/entry/action/affects/llm/level/failure/governance + uiImpact），ID 唯一（实测无重复）。

**缺口**
- ⚠️ **统计数字与实际不符**：代码实测 `COMMANDS.length = 88`（System 类 11 条，含 S11 `sweepVisualGaps`），但 `harness.ts:49`/`:189` 注释与 HARNESS.md §4 均写"87 条"。`COMMAND_COUNTS.total` 运行时为 88，注释仍写 87。
- ⚠️ **`entry` 行号会随代码演进失准**：如 `CMD-N01` 标 `director.ts:87`，硬编码行号是定位辅助而非契约，维护成本高且易腐化。
- ⚠️ **`affects` 是自然语言**（如 "chapters/nextChapter/账本全集"），非结构化路径，`classifyChange`（statechange.ts:63）实际只读 `field` 启发式，**不消费 `affects`**——该字段仅供人读，未驱动分级。

### 2.2 足够使用（可用性）—— 核心查询够用，3 个导出函数是死代码

**实际被调用**：`getCommand`（被 statechange/steering/brain/MemoryAuditModal 调用）、`commandTooltip`（前端徽章悬浮）、`COMMAND_COUNTS`。够支撑"审计日志挂 commandId + UI 悬浮解释"。

**死代码**（全项目零调用，仅 harness.ts 内定义）：
- `commandByEntry`（harness.ts:175）—— 按 `entry` 精确串反查，但 `entry` 含行号描述，路由层从不构造该串反查，而是直接传 `commandId` 字符串。
- `commandsByGovernance`（harness.ts:180）—— 按治理点过滤，无人用。
- `levelOf`（harness.ts:185）—— statechange 用 `classifyChange` 内部调 `getCommand`，不走 `levelOf`。

> 这三个函数是"为未来中枢调度预留"的接口，当前是空转的 API 表面。

### 2.3 足够明确 —— 主体明确，但 failure 字段有大量空缺

**明确的部分**：`level`（L0–L3 破坏性递增，定义清晰）、`governance`（gate/audit/schedule/control/none 组合）、`trigger` 四源划分都明确。

**不明确的部分**：
- ⚠️ **`failure` 字段约 1/3 写 "—"**（如 N13/N15、W02–W08、W17、L02/L05–L10、M 多条、Q 全部）。这些指令当然可能失败（LLM 超时、saveWorld IO 错误），但失败语义未描述。查询类写 "—" 尚可，但 W05/W06（expandArc）这类 LLM 动作写 "—" 就丢失了"失败后状态如何"的关键信息。
- `llm` 字段在文档里有温度参数（如 `exec 0.8`），代码 `CommandLLM` 类型只保留角色（exec/brain/image/video/none/conditional），**温度被丢弃**，实际温度由 `modelconfig.ts` 的 `taskOpts` 另管——两处需手动保持一致，存在漂移风险。

**问题一结论**：登记覆盖面完备、字段结构清晰，作为"审计锚点 + UI 解释"足够使用；但统计数字过时、3 个查询函数空转、`failure`/`affects` 字段半结构化导致"声明完备、可机读性不足"。**明确性中等偏上，可用性中等。**

## 三、问题二：指令的功能设计是否合理？

### 3.1 合理的设计

- **分级 L0–L3（按破坏性而非频率）**：L0 只读/可重建、L1 改未来计划、L2 改已落定内容（可经 chapterDeltas 回滚）、L3 全局不可逆。实测 L3 仅 2 条（N08 删章、S03 级联删章），破坏面收敛得当。
- **治理点四象限 + none**：gate（写前）/audit（留痕）/schedule（排队）/control（可停）正交，可组合。
- **触发源四分**：user/ai/system/brain 区分了"谁发起"，配合 `actor` 字段可追溯。
- **单一写接口收敛意图**：`applyStateChange`（statechange.ts:94）把"分级→预检→日志→对齐→落盘"收口，设计上正确。

### 3.2 设计与实现的脱节（合理但不彻底）

- ⚠️ **`governance` 字段是"声明性"的，不驱动自动行为**。四类治理点实际承担者与标签脱钩：
  - `gate`：声称覆盖所有 L2/L3 写指令，但 `gateChange`/`applyStateChangeAsync` **全项目零调用**（见第四节）。写前审查未接线。
  - `audit`：靠 `logChange`/`logCommandChange` 手动传 `commandId`，**非强制**——核心记账层 `chronicler.ts`（L01/L02/L05）**完全没有 logChange 调用**（实测 chronicler.ts 无 commandId/logChange），账本变更审计混在 commitChapter 的 `CMD-N02` 条目里，L01/L02/L05 的 audit 标签名存实亡。
  - `schedule`：靠 `limiter` + `withTitleLock`，与 governance 标签无程序关联。
  - `control`：靠 `stopFlags`/`interrupts` 内存 Map，与标签无关联。
- ⚠️ **`applyStateChange` 未覆盖核心写章管线**。grep 显示 `applyStateChange` 仅在 routes.ts 的"用户编辑类"端点（伏笔/蓝图/章纲/世界书/字段锁/提案/媒体/完整性）使用；而 director 的 `commitChapter`/`settleChapter`/`editChapter`/`regenerateChapter`/`rollbackChapter`/`deleteChapter`、planner 的 `expandArc`/`handleArcBoundary`、chronicler 全部**直接操作 world 引用 + saveWorld**，绕过统一接口。这正是 HARNESS.md §5 P3"收敛状态写"尚未完成的体现——当前 harness 是"注册表 + 部分审计"，不是"统一写闸门"。

**问题二结论**：分级与治理点的**概念设计合理**，但 `governance` 字段当前是"标签而非开关"——四类治理点的实际行为由分散的机制（limiter/lock/flags/logChange）承担，与指令表无程序耦合；审计对账本层（chronicler）覆盖缺失。**设计合理但落地不彻底，处于"P1 任务画像"阶段。**

## 四、问题三：流程是否完全可控？会不会死锁/异常/崩溃/混乱？

逐层分析，**整体可控性良好，无死锁；但有两处自认缺陷 + 闸门空转 + 审计断点需关注。**

### 4.1 写章管线（writeOneChapter / reviewFixLoop）—— 可控 ✅

- **4 个阶段边界打断检查**（director.ts:352/375/389 + retryChapter:600/624/636）：写作前/写作后/审查后/提交前，命中即抛 `InterruptedError`，**草稿未 commit，零污染**。
- **修复循环有上界**：`reviewFixLoop` `fixRounds < 2`（director.ts:447），patch/rewrite 各最多 2 轮，不会无限循环。
- **requirePass 零落盘**：审查未过抛 `ReviewFailedError`，commit 前不 push chapter、不推进 nextChapter（director.ts:396–399）。
- **commit 原子性**：push chapter → settleChapter → chapterDeltas 快照 → nextChapter++ → 边界 → saveWorld → checkpoint，顺序合理；`nextChapter++` 前置于边界处理是有意为之（注释说明防章号重叠）。

### 4.2 自动连载（runAuto）—— 可控，熔断完善 ✅

- **7 种停止条件**（autorun.ts）：用户停止(116)、用户暂停(118)、全书完结(126)、打断(172)、审查未过暂存暂停(175)、配额错误首次即停(210)、连续错误 ≥3 停(215)。
- **评分熔断**：连续 2 章低于地板分 或 低于 stopAvgScore 即停（:153）。
- **暂存区 git 语义**：ReviewFailed → 草稿进 pending-chapter.json + 质量债务登记（锁内独立事务，:186），停下等人工重试/跳过/停止。
- **断点恢复**：会话状态 autorun-session.json + checkpoint.jsonl；服务重启 `resumeAutoSessions`（routes.ts:2067）扫描 running 会话续跑。

### 4.3 并发与锁（withTitleLock）—— 无死锁 ✅，但需注意不可重入

- `withTitleLock`（titlelock.ts）是 Promise 链式串行队列：`prev.then(fn, fn)` 确保**前次失败不阻塞后续**（fn 同时作 resolve/reject handler），`finally` 清理 key。实现正确。
- **不可重入**：若在锁内再次 `withTitleLock(同 key)` 会死锁（内层 fn 等外层 guard resolve，外层 fn 等内层完成）。但实测 director/planner/chronicler **内部均不调用 withTitleLock**（grep 确认），写章管线在锁内操作的是同一 world 引用，不重入。**当前无死锁路径。**
- `activeAuto` Set（routes.ts:75）防双跑：auto/start 同书名 409 拒绝；resumeAutoSessions 检查 `activeAuto.has` 防重复恢复。
- ⚠️ **边缘**：`activeAuto` 是内存态，服务崩溃时丢失——但重启后空集 + resumeAutoSessions 重扫，可自愈，非缺陷。

### 4.4 限流器（limiter）—— 无死锁、无超额 ✅

- 并发信号量 FIFO（waiters 队列）+ RPM 滑动窗口。`acquireRpm` 的 check 与 push 之间**无 await**（同步段），不会并发超额 push。`finally` 必释放并发槽。排队语义，不主动 429。

### 4.5 状态闸门（gate）—— ⚠️ 完全未接线（空转，非崩溃风险）

- `brain.gateChange`（brain.ts:144）与 `statechange.applyStateChangeAsync`（:126）**全项目零调用**。routes.ts 所有写操作用同步 `applyStateChange`（不带 gate opts）。
- 后果：`AGNES_BRAIN_GATE=on` 时**只有章末一致性审查**（`brainReviewAfterCommit`，commit 后）会触发，**L2/L3 状态变更的写前 gate 从不执行**。即 harness 声称的"gate 写前审查"在状态变更路径上是空声明。
- 风险定性：**这不是崩溃/死锁风险，而是"安全网缺失"**——闸门设计为"加保险非拦路虎"（失败降级放行），故即便接线也不会阻塞主链路；但当前等于保险未装。

### 4.6 弧边界处理（handleArcBoundary）—— ⚠️ 自认缺陷，重试不可靠（连锁严重，见第五节深挖 C）

- 文档（HARNESS.md:87）与代码注释自标"失败被 catch 不重试（缺陷）"。
- 实测（planner.ts:260）：`arc.summary=summarizeRange` → `arc.status="done"` → 卷摘要 → `updateCompass`（内部全 try-catch 静默，不抛）→ `expandArc`。
- 风险定性：**影响数据完整性（卷摘要/指南针可能缺失），不影响正文与连载推进**，不会卡死崩溃。commitChapter 的 catch（director.ts:551）确保不阻塞存档。

### 4.7 审计完整性 —— ⚠️ 账本层断点

- `changeLog` 上限 500（slice(-500)）、`qualityDebt` 上限 200（slice(-200)），防无限增长 ✅。
- ⚠️ chronicler.ts（L01 settleChapter / L02 applySettle / L05 resetChapterLedger）**无任何 logChange/commandId**，账本变更审计混在 commitChapter 的 `CMD-N02` 一条里。L01/L02/L05 声称 `audit`/`gate` 治理，实际无独立审计条目、无 gate。
- ⚠️ `commandId` 靠调用方手动传，**无强制校验**——传错/漏传不会报错（`getCommand` 返回 undefined 静默降级 L0）。

### 4.8 异常吞噬模式 —— 设计意图，但降低可观测性

大量 `catch { /* 静默/不阻塞 */ }`（ensureResearch、healLegacyStory、ensureChapterPlan、updateCompass、handleArcBoundary、brain 降级、impactReport LLM 失败等）。这是"写作主链路绝不阻塞"的有意设计，**保证了不崩溃**，但累积效果是：辅助链路（考据/自愈/指南针/弧摘要/中枢审查）失败时**仅部分有 console.warn，部分完全静默**，故障可观测性偏低，问题易潜伏。

### 4.9 可控性矩阵

| 维度 | 评估 |
|---|---|
| 死锁 | ✅ 无。锁不可重入但无重入路径；限流 FIFO 正确 |
| 崩溃 | ✅ 低风险。多重 try-catch 兜底，主链路绝不阻塞 |
| 异常 | ✅ 可控。7 种熔断 + 暂存区零污染 + 断点恢复 |
| 混乱 | ⚠️ 中风险。闸门空转 + 审计账本断点 + 弧边界重试不可靠 + 静默吞噬多 |

**流程在"能跑、不卡、不崩"意义上完全可控；但在"治理声明全部兑现、故障可追溯"意义上未完全可控**——gate 是空声明、chronicler 审计断点、handleArcBoundary 卷摘要可能永久缺失。这些都不致死锁/崩溃，但属"隐性数据/治理缺口"。

## 五、深入探讨：根因、连锁与定性修正

### 5.1 深挖 A：applyStateChange 是"事后审计器"，P3 统一写的本质未完成

`statechange.ts:92` 注释直言：

> 本实现接受「调用方已应用变更」的 w（内存引用），field 仅作日志/分级描述——这是收编既有写点的最小侵入方式。

实际调用模式（以 `/api/novel/auto/skip` 为例，routes.ts:1129-1140）：

```ts
clearPendingChapter(title);          // 先改磁盘
plans.splice(pi, 1);                 // 先改 world 内存
w.nextChapter = ...;                 // 先改 world 内存
applyStateChange(w, { ... });        // 最后才"分级 + 日志 + 落盘"
finalizeStateChange(w, { ok: true }); // alignWorld + saveWorld
```

**根因**：这是"最小侵入收编"策略——不重写 routes 既有逻辑，只在尾部加审计/落盘。代价是 `applyStateChange` 从未真正"写"字段，它只是**收尾器**。

**深层风险**（比"gate 空转"更本质）：即便未来给 `applyStateChangeAsync` 接线 gate，gate 也在**字段已被调用方改脏之后**才审查。拒绝时只能靠"不 `saveWorld`"撤销磁盘，但 **`world` 内存引用已污染**。在 `withTitleLock` 串行下，同一请求生命周期内后续若再读 `world`（如连环操作），会基于脏状态决策。这解释了为什么 gate 至今没接线——接了也是"半截拦截"，且会破坏"调用方先改"的既有契约。**真正完成 P3 需要把字段写入也收口进 `applyStateChange`，而非仅收口审计。**

### 5.2 深挖 B：governance 标签与实际能力的系统性 drift（以 control 为例）

第三节说"标签是声明非开关"，本节找到实证与反证：

| 指令 | harness 标 governance | 实际能力 | drift |
|---|---|---|---|
| N05 regenerateChapter | `gate+audit`（无 control） | 3 处 `checkInterrupt`（director.ts:1133/1153/1186），**可打断** | 漏标 control |
| N07 rollbackChapter | `gate+audit` | 无 LLM 写作，确定性版本切换，**无需打断** | 合理（但无 control 标签也确实不可打断） |
| N10 reviewFixLoop | `none` | 内嵌于 N02，继承 N02 的打断检查 | none 合理 |
| W09 handleArcBoundary | `gate+schedule` | 同步跟随 commitChapter，**无独立排队** | schedule 名不副实 |

**根因**：control 能力由 `checkInterrupt` 基础设施提供，凡调用它的就可打断，与 `governance` 字段无关。schedule 由 `limiter`+`withTitleLock` 提供，但 W09 这类同步动作并无排队实体。**drift 不是 bug，是"标签先于实现"的设计债**——HARNESS.md §5 把 gate 接入列为 P2、schedule 统一列为 P3，当前确实还在 P1。

**风险**：若未来中枢模型（brain）或调度器按 `governance` 字段驱动行为（这正是 harness 设计意图），N05 会被当作"不可打断"而放弃发送 interrupt，W09 会被当作"有排队"而误判并发安全。

### 5.3 深挖 C：handleArcBoundary 的连锁——卷摘要缺失 → 全书永不自然完结

这是"卷摘要可能永久缺失"的二阶后果，比数据残缺更严重。完整因果链：

```
handleArcBoundary (planner.ts:260)
  ├─ summarizeRange(弧) ✅
  ├─ arc.status = "done"        ← 已置位
  ├─ summarizeRange(卷) :274    ← 若此处抛错
  │     ↓
  │   arc 已 done / vol 未 done / 异常上抛
  │     ↓
  │   被 commitChapter:551 catch（"不阻塞存档"）
  │     ↓
  └─ markChapterDone 下次不再触发该弧边界（arc 已 done）
        ↓
      vol.summary 永久缺失 + compass 未更新
        ↓
      autoRepair 不碰 blueprint.volumes（integrity.ts:218 只清孤儿，不补卷摘要）
        ↓
      isBookComplete = vols.every(status==="done")  (planner.ts:345)  永为 false
        ↓
      连载失去"自然完结"判定 → 一路跑到 maxChapters=30 硬上限才停
```

**定性**：这不是崩溃，是**结构性沉默失败**——全书卷边界数据残缺 + 完结判定失效 + 指南针不校准（长篇跑偏风险）。用户看到的是"连载莫名写满 30 章停下"而非"卷摘要丢了"。可观测性极低（仅 `updateCompass` 的静默 catch 留痕，卷摘要失败甚至无 console.warn）。

**修复方向（讨论层面）**：三选一——① 调换顺序为先 `summarizeRange(卷)` 再 `vol.status="done"`（失败可重入）；② `autoRepair` 增补"卷弧全 done 但 vol.summary 空 → 标记 finding"；③ `handleArcBoundary` 失败后写一个"待重试"标记供下回合消费（类比暂存区机制）。当前三者皆无。

### 5.4 深挖 D：审计的两道暗门

**暗门 1 — `commandId` 无校验**：`getCommand` 对未知 ID 返回 `undefined`，`logCommandChange` 静默用 `entry.commandId ?? cmd?.id`（steering.ts:50），手误写成 `"CMD-M2"` 不报错，审计条目 `kind` 变成错误字符串仍记录。routes.ts 里 commandId 全是裸字符串字面量（如 `"CMD-M02"`、`"CMD-L13"`），无编译期校验，无运行期告警。

**暗门 2 — `changeLog` 上限 500 截断**（steering.ts:39 `list.slice(-500)`）：
- 量化：30 章连载，每章至少 `chapter-commit`(1) + `brain-disposition`(1) + 债务/编辑若干 ≈ 每章 2-4 条 → 60-120 条；加上世界编辑/媒体/伏笔操作，长篇轻松破 500。
- 后果：**早期章节审计被丢弃保最近**——"所有操作可追溯"在长篇下打折扣。chapterDeltas（账本快照）虽不受 500 限制（是 Map 不截断），但 changeLog 的"谁在何时为何改了什么"会失忆。
- 矛盾点：HARNESS.md §1 称 audit"保证完整性"，但 500 上限是防无限增长的工程妥协，二者未在文档中调和。

### 5.5 深挖 E：两套守卫并行的不一致

| 守卫 | 位置 | 覆盖范围 | 路径 |
|---|---|---|---|
| `deterministicGuard` | statechange.ts:41 | 仅角色 `status`/`look` 字段锁 | routes 用户编辑类（经 applyStateChange） |
| `applySettle` 内置守卫 | chronicler.ts:108- | 字段锁 + 别名归一 + 伏笔 ID 精确匹配 + 文本去重 + 长度 clamp | director 写章管线（不经 applyStateChange） |

**根因**：两套守卫作用于**互不相交的路径**——applyStateChange 路径（用户编辑）与 commitChapter→settleChapter 路径（AI 记账）各自独立。L02 `applySettle` 标 `gate` 治理，但 statechange 的 gate 完全管不到它；它的"守卫"是 applySettle 内联的，与 governance 无程序关联。

**风险**：新增字段守卫需改两处且易遗漏；若以"gate 指令"清单（harness 声称 L01-L07 有 gate）做安全审计，会误以为账本写入经过 statechange 闸门，实际走的是 chronicler 内联守卫——**两套守卫的严格程度不同**（deterministicGuard 只看锁，applySettle 还做去重/归一/clamp），安全分析若假设统一会失准。

### 5.6 可控性再定性（修正）

第四节结论"无死锁、低崩溃、主链路绝不阻塞"——**维持**。本节补充三点：

1. **N05/N07 的零污染验证**：regenerateChapter 有 3 阶段打断检查（写作前/写作后审查前/审查后结算前），未 `saveWorld` 前抛 `InterruptedError` 不落盘；rollbackChapter 无 LLM 写作、确定性版本切换，无需打断。两者均安全。

2. **新增"结构性沉默失败"类别**：handleArcBoundary 卷摘要缺失（5.3）不触发任何熔断、不留显式告警、不被 autoRepair 覆盖、导致完结判定失效——这是比"异常吞噬"更隐蔽的失控形态：**系统继续运转但已偏离正确状态，且无信号**。第四节的"异常吞噬降低可观测性"在此具体化为一条可触发的失败链。

3. **"声明-实现 drift"是可控性的认知风险**：governance 标签、failure 字段、计数注释（87 vs 88）等声明性内容与实现的偏差，会让维护者/中枢模型对系统能力产生错误预期。这不是运行时失控，是**工程治理层面的"可信度损耗"**——在"流程可控性"维度上，它削弱了"按文档推断行为"的可靠性。

**修正后总判断**：运行时层面（死锁/崩溃/卡死）可控性**良好**；数据完整性层面（卷摘要/审计截断）有**隐性缺口**；治理声明层面（gate/audit/control 标签）与实现**系统性未对齐**。三者共同构成"能跑不崩，但治理承诺未兑现且部分失败静默"的现状。

## 七、总体结论

1. **指令完备性**：登记面完备、结构清晰，作"审计锚点 + UI 解释"够用；但统计过时、3 个查询函数空转、`failure`/`affects` 半结构化，**机读性与明确性中等**。

## 八、第二阶段深入：L3 删章级联 / 媒体异步任务 / 服务重启恢复

在第一阶段的"声明-实现 drift"与"治理缺口"之外，本阶段深入运行时最危险的三个路径——不可逆操作（L3 删章）、异步任务生命周期（媒体生成/视频轮询）、崩溃恢复（服务重启续跑），检验它们在"异常、崩溃、混乱"维度的实际表现。

### 8.1 L3 删章级联（deleteChapterCascade）—— git revert 语义扎实，但有一处一致性缺口

`integrity.ts:301` 的级联删章是全项目唯一的 L3 不可逆路径，设计为 git revert 语义，核心逻辑经得起推敲：

**扎实之处**
- **变更快照逆操作**（integrity.ts:34 `applyChapterDeltaRevert`）：删章前先按 `chapterDeltas[index]` 回退——本章回收的伏笔恢复为回收前状态、角色 status/look 恢复旧值、全局 current/弧线恢复。每项都有**字段级冲突检查**（`hasLaterChange`，:18）：若后续章节改过同一字段，则保留后续值并报告，避免"回退覆盖了更新的既成事实"。
- **无快照降级**（:321）：旧存档无 chapterDeltas 时降级为基础清理，并产 `delta-missing` warning finding 交用户核对——不假装能恢复，诚实降级。
- **伏笔保守策略**（:331）：未回收的活跃伏笔随章删除（danger finding），已回收的保留留痕（warning finding）——区分对待，不盲目删。
- **index 空洞原则**（:363）：仅删尾章回退 nextChapter，删中间章保留空洞、绝不重排 index。所有按 index 引用的账本（时间线/摘要/计划）零迁移，避免连锁重排。
- **媒体去重删除**（:307）：仅删不被全书其他章节引用的 media path，防止删章连带删掉共享资源。

**一致性缺口**
- ⚠️ **删章不触发弧边界重算**：`deleteChapterCascade` 删掉 `chapterPlans[index]`（:355）但**不检查该章是否是所属弧的最后一章、不回退 arc.status**。若删掉的是弧的最后一章，`arc` 仍为 `done`（commitChapter 时 markChapterDone 置的），而该弧的 chapterPlans 已残缺。后果：
  - 该弧 summary 已生成（commit 时 handleArcBoundary 做的）但弧内章数减少——摘要与正文不符。
  - 更严重的是与 5.3 的 handleArcBoundary 缺陷叠加：若该弧卷摘要本就缺失（5.3），删章后更无法通过任何路径补全。
- ⚠️ **删中间章后 chapterDeltas 的 hasLaterChange 语义偏移**：`hasLaterChange`（:18）按 `i > chapterIndex` 查后续 delta，但删中间章后 index 空洞存在，后续章的 delta 仍按原 index 存储——回退逻辑本身正确（按 index 比较），但**若用户删章后又重写该空洞章**（routes 允许按 index 写），新写的 delta 会覆盖旧 delta，旧的"后续章冲突检查"基准丢失。这是 index 空洞设计的固有副作用，非 bug 但需文档警示。

**定性**：L3 删章是全项目设计最严谨的路径之一，git revert 语义 + 字段级冲突检查 + 保守伏笔策略 + 诚实降级，数据一致性保护到位。缺口在"删章后弧/卷状态不重算"——属于 5.3 handleArcBoundary 缺陷的同源延伸（弧边界处理在删章路径缺失）。

### 8.2 媒体异步任务生命周期 —— 无死循环，但有两处"永久 pending"风险

媒体生成是 L0（不破坏叙事），但异步任务若失控会烧配额或留孤儿状态。逐路径检验：

**插画异步生成（routes.ts:1477-1543）**
- 生成循环 `for (let attempt = 0; ; attempt++)`（:1487）看似无限，但**非 429 错误直接 throw 跳出**（:1503），429 仅 `attempt === 0` 重试一次（:1498）——**不会死循环**。
- `Promise.allSettled`（:1479）多张并发，单张失败不阻塞其余——隔离正确。
- 完成后锁内回写（:1506），回写前检查"媒体/章节是否已被删"（:1510），已被删则丢弃产物删盘——**防孤儿残留**。
- `imageGenTasks` 内存表（routes.ts:88）记录生成中状态，服务重启时 `/media/status` 检测到 pending 但不在表内 → 标记 failed（:1570）——**中断可恢复**。

**视频轮询（videos.ts:110 + routes.ts:1586）**
- ⚠️ **风险 1：视频任务无服务端超时回收**。`pollVideoTask`（videos.ts:110）是**单次查询**（无内部循环），由前端 `/media/status` 轮询驱动。若视频服务端任务长时间 queued/in_progress（或前端关闭页面停止轮询），该 media 条目**永久停在 pending**，videoId 永不清理。与插画的"服务重启标记 failed"不同——视频的 pending 状态在 `/media/status` 中（:1564）只对"无 videoId"的插画做中断检测，**有 videoId 的视频即使服务重启也不会被标记 failed**（:1564 的 `if (!media.videoId)` 分支跳过视频）。
  - 后果：视频生成失败但任务未返回 failed（如服务端超时无响应），media 永远 pending，用户需手动删除。非崩溃，但状态混乱。
- ⚠️ **风险 2：429 永久降级为 rate_limited 返回 pending**（videos.ts:116/126）。`pollVideoTask` 对 429 和"!res.ok || !data"都返回 `rate_limited`（:116/126），前端收到 `rateLimited: true`（routes.ts:1588）继续轮询。若视频服务持续 429，前端会**无限轮询**（无客户端轮询次数上限的文档约束）。配额不烧（查询不生成），但前端资源占用。

**角色视觉自动生成（ensureCharacterVisuals，routes.ts:130）**
- `visualInFlight` Set 进程级去重（:133），同一角色同时只一个任务——防重复烧配额。
- `visualTriedAt` 冷却 60s（:143），失败也置位——防高频重试。
- fire-and-forget + 内部短事务落盘——不阻塞调用方。
- ✅ 可控，无失控路径。

**中枢视觉巡检（sweepVisualGaps，routes.ts:240）**
- `setInterval` 60s（:260），幂等保护 `if (visualSweepTimer) return`（:259）——重复启动不叠加。
- try-catch 包裹（:261），异常不崩定时器。
- 复用 `visualTriedAt` 冷却 + `visualInFlight` 去重——与入口触发共用防烧机制。
- ✅ 可控。

**媒体层定性**：无死循环（插画重试有界、视频单次查询）、无配额失控（去重+冷却+限流三重防烧）；但视频任务有"永久 pending"风险（无服务端超时回收 + 重启不标记视频 failed），属状态混乱非崩溃。这是媒体层唯一需要关注的治理缺口。

### 8.3 服务重启恢复（resumeAutoSessions）—— 可恢复，但重启窗口有状态丢失

`routes.ts:2067` 的 `resumeAutoSessions` 扫描 `data/*/autorun-session.json`，`status==="running"` 的后台续跑：

**可恢复**
- 会话状态持久化（autorun-session.json）+ checkpoint.jsonl 双保险。
- 续跑前 `activeAuto.has(key)` 检查（:2080）防同进程重复恢复。
- 后台续跑用 `runAutoInBackground`（:2041），无 SSE 消费者时进度写 session.json。
- 断点修正（routes.ts:1054-1064）：nextChapter ≤ maxIdx 时修正为 maxIdx+1，防"章节已落盘但计数未推进"的重复写章。

**重启窗口的状态丢失**
- ⚠️ `stopFlags`/`pauseFlags`/`interrupts`/`activeAuto`/`imageGenTasks`/`visualInFlight`/`visualTasks` 全是**内存态**，服务重启全部丢失。
  - `stopFlags` 丢失：用户重启前点的"停止"失效，running 会话会被 resumeAutoSessions 自动续跑——**与用户意图相悖**。但 session.json 的 `status` 在 stopAuto 时未改写（stopAuto 仅置内存 flag），重启后仍是 running → 续跑。这是一个**用户预期 vs 实际行为**的偏差：用户以为"停止了"，重启后又跑起来。
  - `interrupts` 丢失：重启后正在写的章节的打断信号消失。但 writeOneChapter 的打断是"阶段边界检查"，重启后续跑是新一次 writeOneChapter 调用，旧打断信号本就无意义——**非缺陷**。
  - `imageGenTasks` 丢失：重启后 `/media/status` 检测 pending 不在表内 → 标记 failed（:1570）——**可自愈**。
  - `visualInFlight` 丢失：重启后 ensureCharacterVisuals 可重新触发（visualTriedAt 冷却后）——**可自愈**。
- ⚠️ **resumeAutoSessions 的并发安全**：它在 `for (const d of readdirSync(dataDir))`（:2070）循环内 `void runAutoInBackground`（:2084）——`void` 不 await，多个故事的恢复**并行启动**。每个 runAutoInBackground 内部用各自 `withTitleLock(key)` 串行，不同书名锁不冲突——**跨书并行安全**。但若同一书名在 data 目录下有多个 slug 映射（理论上 slugify 幂等），`activeAuto` 防双跑——**安全**。

**恢复层定性**：会话恢复机制健全（持久化+断点修正+防双跑），核心写章数据不丢。主要偏差是"stopFlags 内存态导致重启后续跑与用户停止意图相悖"——这是 design choice（内存信号不持久化的代价），非 bug，但应在文档中明示"停止后需 clear-session 才能防止重启续跑"。

## 九、综合终判

经过两阶段深入（声明-实现 drift + 运行时危险路径），对最初三个问题的终判：

**问题一（指令完备/详细/可用/明确）**：登记完备、结构清晰，但统计过时（87→88）、3 函数空转、failure/affects 半结构化。作为"审计锚点+UI 解释"够用，作为"可机读契约"不足。**评定：中等偏上。**

**问题二（功能设计合理）**：分级与治理点概念合理，L3 删章的 git revert 语义设计严谨（字段级冲突检查+诚实降级）。但 governance 是声明标签非行为开关，账本层审计断点，applyStateChange 是事后审计器非写前拦截器，P3 未完成。**评定：设计合理，落地 P1-P2。**

**问题三（流程可控/死锁/崩溃/混乱）**：
- **死锁**：✅ 无。锁不可重入但无重入路径；限流 FIFO 正确；异步任务无死循环。
- **崩溃**：✅ 低风险。多重 try-catch 兜底，主链路绝不阻塞，定时器有幂等+try-catch。
- **异常**：✅ 可控。7 种熔断+暂存区零污染+断点恢复+L3 诚实降级。
- **混乱**：⚠️ 中风险。闸门空转+审计断点+弧边界重试不可靠（→完结判定失效）+视频永久 pending+stopFlags 重启丢失+声明-实现 drift。

**最终定性**：**运行时安全（不卡、不崩、不死循环），数据完整性有隐性缺口（弧/卷摘要、视频 pending），治理声明系统性未兑现（gate 空转、audit 断点、标签 drift）。** 这是一套"能跑且安全，但治理承诺是期货"的系统——距 HARNESS.md 自述的 P3 终态（统一写闸门+全量治理）有明确的、可逐项修复的缺口，无致命失控风险。
